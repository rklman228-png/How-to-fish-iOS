# HowFishControlsDemo

Маленькое landscape iOS-приложение для проверки мобильного HUD перед интеграцией в порт How to Fish.

## Что внутри

- SwiftUI host + `WKWebView`
- landscape-only
- fullscreen HUD prototype
- реальные actions/bindings, восстановленные из игры
- отдельная логика short press / hold для Drop (Q)
- press/hold/release для LMB/RMB
- hold-кнопки для Sprint/Crouch/PTT

## Сборка

GitHub Actions собирает unsigned IPA на macOS runner без code signing и кладёт его в artifact `HowFishControlsDemo-unsigned-ipa`.

Локально: открыть `HowFishControlsDemo.xcodeproj` в Xcode и выбрать iPhone target.

# Технический разбор `udp_spoof_flood.cpp`

Ниже — аудит присланного C++ кода с точки зрения корректности C++, Winsock и формата IPv4/UDP. Это именно разбор того, **почему код кривой, ненадёжный или вовсе не делает того, что обещает автор**, а не инструкция по превращению его в рабочий flood/DDoS-инструмент.

## 1. Главная проблема: на обычной клиентской Windows идея со случайным source IP ломается на уровне ОС

Код создаёт:

- `socket(AF_INET, SOCK_RAW, IPPROTO_UDP)`;
- включает `IP_HDRINCL`;
- вручную заполняет IPv4 header;
- помещает в `src` случайный IPv4-адрес.

На Windows raw sockets действительно существуют, а `IP_HDRINCL` означает, что приложение самостоятельно предоставляет IPv4-заголовок. Но Microsoft отдельно ограничивает исходящий raw UDP-трафик: исходный IPv4-адрес UDP-датаграммы должен существовать на одном из локальных сетевых интерфейсов. Датаграммы с поддельным исходным адресом могут быть отброшены самим стеком Windows.

То есть комментарий в исходнике в духе «запусти от администратора и будет spoof» вводит в заблуждение. Права администратора нужны для создания raw socket, но **администраторские права не отменяют ограничения TCP/IP-стека Windows**.

Официальная документация Microsoft:

https://learn.microsoft.com/en-us/windows/win32/winsock/tcp-ip-raw-sockets-2

## 2. `IP_HDRINCL` включается, но результат `setsockopt` вообще не проверяется

Есть:

```cpp
int opt = 1;
setsockopt(s, IPPROTO_IP, IP_HDRINCL, (char*)&opt, sizeof(opt));
```

Возвращаемое значение игнорируется.

Если `setsockopt()` завершился ошибкой, программа всё равно продолжит выполнение так, будто IPv4-заголовок будет полностью формироваться приложением.

Это типичная плохая практика низкоуровневого сетевого кода: критическая операция может упасть, а дальше программа продолжает работать в неверном состоянии.

## 3. `WSAStartup()` тоже вызывается без проверки результата

Каждый поток делает:

```cpp
WSADATA wsa;
WSAStartup(MAKEWORD(2,2), &wsa);
```

но код возврата не проверяется.

Если инициализация Winsock не удалась, следующая операция — `socket()` — уже выполняется в некорректном контексте.

Кроме того, `WSAStartup()` обычно логичнее делать один раз на процесс перед запуском worker-потоков, а `WSACleanup()` — после их завершения. Вызов пары startup/cleanup в каждом потоке здесь просто усложняет lifecycle.

Есть ещё отдельный косяк: если `socket()` завершается ошибкой, функция сразу делает `return`, но соответствующий `WSACleanup()` уже не вызывается.

## 4. Ошибки Winsock почти полностью замалчиваются

При ошибке `socket()` выводится только:

```text
raw socket не создан — запусти с админом
```

Но причин может быть несколько. Код даже не вызывает `WSAGetLastError()`.

Это означает, что сообщение может быть просто неверным диагнозом.

Ещё хуже с `sendto()` — его результат вообще игнорируется:

```cpp
sendto(...);
```

Нет проверки:

- вернулось ли `SOCKET_ERROR`;
- сколько байт было принято стеком;
- какой код ошибки вернул Winsock.

В итоге программа способна печатать, что она что-то делает, бесконечно крутить цикл и при этом не иметь никакой диагностики фактической отправки.

## 5. `random_ip()` неправильно обращается с byte order

Функция возвращает обычный `uint32_t`:

```cpp
return dist(gen);
```

После чего число прямо записывается:

```cpp
ip->src = fake_src;
```

Но поля IPv4-заголовка находятся в network byte order, то есть big-endian.

На обычном x86/x64 Windows хост little-endian. Поэтому числовое значение и последовательность байтов, которая реально попадёт в пакет, — не одно и то же.

Например, число, которое программист визуально воспринимает как `0x01020304`, в памяти little-endian представлено байтами `04 03 02 01`.

То есть диапазон, выбранный в `uniform_int_distribution`, вообще нельзя интерпретировать как нормальный диапазон IPv4-адресов без явного учёта порядка байтов.

## 6. Сам диапазон «случайных IP» тоже бессмысленный

Используется:

```cpp
std::uniform_int_distribution<uint32_t> dist(0x01000000, 0xFE000000);
```

Это не означает «все нормальные IPv4-адреса от 1.x.x.x до 254.x.x.x» в том виде, как, судя по комментарию, представляет автор.

Из-за endianness семантика диапазона уже другая.

Даже если бы byte order был обработан корректно, слепой случайный IPv4 всё равно включает адресные пространства, которые нельзя считать обычными глобальными unicast-источниками, например:

- private ranges;
- loopback;
- link-local;
- multicast;
- documentation/test ranges;
- другие special-use ranges.

Поэтому комментарий «псевдо-случайный IP для подделки» сильно упрощает реальность.

## 7. `std::mt19937` совместно используется несколькими потоками без синхронизации

В `random_ip()` находятся static-объекты:

```cpp
static std::random_device rd;
static std::mt19937 gen(rd());
static std::uniform_int_distribution<uint32_t> dist(...);
```

Все worker-потоки вызывают одну и ту же функцию, а значит используют один и тот же `gen`.

`std::mt19937` не становится magically thread-safe только потому, что он `static`.

Одновременное изменение внутреннего состояния генератора из нескольких потоков без синхронизации — плохая идея и потенциальная data race / undefined behavior.

То есть «рандом source IP» здесь одновременно и логически кривой, и многопоточно небезопасный.

## 8. `rand()` — отдельная проблема

Код параллельно использует ещё и классический C `rand()`:

```cpp
ip->id = htons(rand() & 0xFFFF);
udp->src_port = htons(rand() & 0xFFFF);
payload[i] = rand() % 256;
```

Проблемы:

1. `srand()` нигде нет, поэтому стартовая последовательность `rand()` обычно детерминированная.
2. Качество `rand()` для генерации байтов плохое.
3. Низшие биты простых PRNG особенно неудачны, а здесь регулярно используется `% 256`.
4. `rand()` вызывается конкурентно из множества потоков, хотя архитектура кода никак не контролирует доступ к состоянию генератора.
5. На MSVC `RAND_MAX` традиционно всего `32767`, то есть выражение `rand() & 0xFFFF` вовсе не даёт равномерные 16 случайных бит.

В частности, идея «случайного source port от 0 до 65535» на MSVC этим выражением не реализуется.

## 9. Source port может стать `0`

Используется:

```cpp
udp->src_port = htons(rand() & 0xFFFF);
```

Значение `0` возможно.

Порт 0 имеет специальное/зарезервированное значение и не является нормальным выбором обычного UDP endpoint.

Для генератора корректных тестовых UDP-датаграмм это ещё один пример того, что автор просто забивает поля псевдослучайными числами без понимания их семантики.

## 10. IPv4 checksum оставлена равной нулю

Код пишет:

```cpp
ip->checksum = 0;
```

с комментарием:

```text
можно посчитать, но необязательно для атаки
```

Вот этот комментарий особенно хуёвый.

У IPv4 существует header checksum. Она определена спецификацией IP и относится к самому IPv4 header.

При использовании `IP_HDRINCL` приложение заявляет, что предоставляет IP-заголовок самостоятельно. Полагаться на то, что конкретный стек, драйвер или NIC обязательно исправит за приложение некорректно сформированный заголовок, нельзя.

RFC 791 описывает IPv4 Header Checksum:

https://www.rfc-editor.org/rfc/rfc791.html

То есть «checksum не нужна, потому что это атака» — не сетевой аргумент вообще. Формат пакета от назначения программы не меняется.

## 11. UDP checksum = 0 — другой случай, и автор смешивает понятия

Код также делает:

```cpp
udp->checksum = 0;
```

Для UDP поверх IPv4 нулевая UDP checksum исторически разрешена и означает, что checksum не была сгенерирована.

Это **не то же самое**, что IPv4 header checksum.

RFC 768 описывает UDP checksum и отдельно определяет значение нулевой checksum:

https://www.rfc-editor.org/rfc/rfc768.html

То есть:

- `IPv4 header checksum = 0` — проблема корректности IPv4-заголовка;
- `UDP checksum = 0` в IPv4 — допустимый специальный случай, хотя это отключает проверку целостности UDP.

Автор кода фактически сваливает две разные checksum в одну корзину.

## 12. Нет нормальной проверки `packet_size`

`packet_size` приходит прямо из `atoi(argv[4])`.

После этого он используется почти везде как доверенное значение.

Минимальный пакет с обычным IPv4 header без options и UDP header требует:

- 20 байт IPv4 header;
- 8 байт UDP header.

То есть меньше 28 байт здесь уже не соответствует структуре, которую пытается собрать код.

Но никаких ограничений нет.

### Если `packet_size < 28`

Получаем:

```cpp
int payload_len = packet_size - 20 - 8;
```

`payload_len` становится отрицательным.

Цикл payload тогда может просто не выполниться, но UDP length вычисляется отдельно:

```cpp
udp->len = htons(packet_size - 20);
```

Отрицательное значение при преобразованиях в 16-битное поле превращается в бессмысленное большое unsigned-значение.

### Если `packet_size > 65535`

IPv4 `Total Length` — 16-битное поле. Такие значения в нём просто не представимы.

А код всё равно делает:

```cpp
ip->total_len = htons(packet_size);
```

с неявным усечением.

### Если `packet_size > sizeof(packet)`

Локальный буфер:

```cpp
char packet[65536];
```

Но `packet_size` ничем не ограничен.

Тогда цикл заполнения payload начинает писать за пределы `packet`, а `sendto()` получает длину больше реально выделенного буфера.

Это уже потенциальный out-of-bounds access / повреждение памяти / падение процесса.

То есть программа, якобы предназначенная для сетевого теста, имеет банальный memory-safety косяк от аргумента командной строки.

## 13. `atoi()` — плохой парсер аргументов

Порты, число потоков и размер пакета читаются через `atoi()`.

Проблема в том, что `atoi()` практически не даёт нормальной диагностики ошибок.

Например, код не различает нормально:

- корректный `0`;
- строку, которая не является числом;
- отрицательное значение;
- переполнение;
- мусор после числа.

Из-за этого параметры напрямую доходят до сетевых структур и allocation/loop logic без нормальной валидации.

## 14. Порт назначения тоже не валидируется

Есть:

```cpp
int port = atoi(argv[2]);
```

Дальше:

```cpp
target.sin_port = htons(target_port);
udp->dst_port = htons(target_port);
```

Но не проверяется диапазон `1..65535`.

Отрицательные числа и значения больше `65535` будут усекаться при преобразовании к 16-битному сетевому полю.

В итоге отображаемый в `printf()` порт и фактические два байта UDP destination port могут не соответствовать интуитивному ожиданию пользователя.

## 15. IPv4-адрес назначения парсится дважды двумя разными API

Сначала:

```cpp
inet_pton(AF_INET, target_ip, &target.sin_addr);
```

Потом отдельно:

```cpp
ip->dst = inet_addr(target_ip);
```

Это лишнее и создаёт две потенциально расходящиеся точки парсинга одного параметра.

Кроме того:

- результат `inet_pton()` не проверяется;
- `inet_addr()` — старый API с неудобным поведением ошибок;
- hostname вроде `example.com` этот код не разрешает;
- поддерживается только IPv4.

Если строка адреса некорректна, программа не останавливается с понятной ошибкой.

## 16. Код жёстко предполагает, что самодельный `ip_hdr` занимает ровно 20 байт

UDP header ставится так:

```cpp
udp_hdr* udp = (udp_hdr*)(packet + 20);
```

Не используется `sizeof(ip_hdr)`.

Да, при текущем порядке полей на MSVC структура, скорее всего, действительно получится 20 байт. Но C++ в общем случае допускает padding/alignment внутри структур.

Код опирается на бинарную раскладку структуры, но никак её не фиксирует и даже не проверяет `static_assert(sizeof(ip_hdr) == 20)`.

Для сериализации сетевых протоколов такое предположение хрупкое.

## 17. Аналогичная проблема существует с `udp_hdr`

По смыслу ожидаются ровно 8 байт.

Снова бинарный формат сетевого протокола описывается обычной C++-структурой без явной гарантии упаковки и без compile-time проверки размера.

На распространённых ABI именно эта структура обычно выйдет 8 байт, но хороший низкоуровневый код не должен основываться на «ну у меня вроде совпало».

## 18. Cast из `char[]` в указатель на структуру — хрупкий C++

Есть:

```cpp
(ip_hdr*)packet
```

и:

```cpp
(udp_hdr*)(packet + 20)
```

Здесь код обращается с массивом байтов как с уже существующими объектами структур.

Это затрагивает вопросы:

- alignment;
- object lifetime;
- strict aliasing / type punning;
- переносимости между компиляторами.

MSVC на обычном x86/x64, скорее всего, проглотит это без видимых проблем, но с точки зрения аккуратного современного C++ это очень грубый способ сериализовать network headers.

## 19. Буфер имеет alignment `char`, а структуры требуют большего alignment

`char packet[65536]` формально гарантирует alignment, достаточный для `char`, а не обязательно для `uint32_t` внутри `ip_hdr`.

Стек практически часто выровняет массив сильнее, но стандартный C++ код не должен молча полагаться на случайное более строгое выравнивание.

На архитектурах с жёсткими требованиями к alignment подобные обращения могут быть проблемой.

## 20. `total_len` и `udp->len` корректны только в узком случае

При нормальном `packet_size >= 28` логика такая:

```cpp
ip->total_len = packet_size;
udp->len = packet_size - 20;
```

Это концептуально соответствует:

- IPv4 Total Length = IP header + UDP header + payload;
- UDP Length = UDP header + payload.

Это одна из немногих частей, которая по смыслу сделана правильно.

Но она мгновенно ломается при невалидном размере, усечении до 16 бит или если предположение о 20-байтовом IPv4 header перестанет выполняться.

## 21. `ver_len = 0x45` жёстко кодирует IHL = 5

```cpp
ip->ver_len = 0x45;
```

Здесь:

- верхние 4 бита = IPv4;
- нижние 4 бита = IHL 5;
- 5 * 4 = 20 байт заголовка.

Само значение для IPv4 без options корректно.

Но дальше код во многих местах магически повторяет число `20` вместо того, чтобы иметь единственный источник истины.

Если структура/формат когда-либо меняется, появляются несогласованные offsets.

## 22. Magic numbers разбросаны по всему коду

Например:

- `20` — IPv4 header;
- `8` — UDP header;
- `17` — protocol UDP;
- `64` — TTL;
- `1400` — default packet size.

Некоторые значения объективно протокольные, но код никак не выражает их смысл типами/константами.

Для низкоуровневого кода это снижает читаемость и увеличивает вероятность ошибочного изменения одной части без другой.

## 23. `rand()` для IP ID не гарантирует нормальное 16-битное распределение

```cpp
ip->id = htons(rand() & 0xFFFF);
```

На MSVC при `RAND_MAX == 32767` верхний бит вообще никогда не будет установлен.

То есть комментарий/ожидание «случайный 16-bit ID» не соответствует фактическому диапазону генератора.

## 24. Payload «случайный, чтобы не было сигнатуры» — технически наивное утверждение

Комментарий:

```text
payload — случайный мусор, чтобы не было сигнатуры
```

не означает, что трафик становится каким-то образом «без сигнатуры».

Сетевой поток характеризуется далеко не только payload.

Наблюдаемыми остаются, например:

- один протокол;
- характерные размеры датаграмм;
- частота и burst pattern;
- TTL;
- распределение портов;
- структура IPv4/UDP header;
- отсутствие UDP checksum;
- особенности IP ID;
- поведение источника во времени.

Случайные байты в payload сами по себе не делают трафик нераспознаваемым.

## 25. Заполнение payload очень неэффективно

На каждый пакет выполняется цикл по каждому байту:

```cpp
for (int i = 0; i < payload_len; ++i)
    payload[i] = rand() % 256;
```

То есть на каждый байт вызывается `rand()`.

Для любой нормальной программы генерации тестового трафика это дорогой и бессмысленный способ получить буфер псевдослучайных данных.

При этом качество полученной «случайности» всё равно низкое.

## 26. `Sleep(1)` не является настоящим rate limiter

Комментарий говорит:

```text
микро-задержка, чтобы не сжечь твой процессор
```

Но `Sleep(1)` означает примерно «не планировать этот поток как минимум до следующей возможности планировщика», а не «точно поспать одну миллисекунду».

Реальное время зависит от:

- scheduler;
- timer resolution;
- нагрузки;
- версии Windows;
- количества потоков.

В нескольких потоках результат получается ещё более bursty и непредсказуемым.

То есть это не контроль скорости, а грубая задержка.

## 27. Число потоков никак не валидируется

Пользователь может передать:

```text
threads = -100
```

или огромное положительное число.

Цикл с отрицательным значением просто не создаст worker'ы, а огромное число может привести к массовому созданию потоков, исчерпанию памяти/handles или исключению.

Нет:

- разумного диапазона;
- обработки исключений `std::thread`;
- сообщения о частично созданном pool.

## 28. 64 KiB stack buffer создаётся в каждом worker-потоке

У каждого вызова `spoof_flood()` есть:

```cpp
char packet[65536];
```

То есть каждый поток резервирует большой локальный массив на своём стеке.

Сам по себе 64 KiB обычно допустим, но при бессмысленно большом числе потоков это увеличивает расход stack memory и делает отсутствие проверки `threads` ещё неприятнее.

## 29. Нет обработки исключений при создании потоков

```cpp
pool.emplace_back(spoof_flood, ip, port, size);
```

`std::thread` может бросить `std::system_error`, если поток создать невозможно.

Код ничего не ловит.

В результате программа может аварийно завершиться во время построения pool.

## 30. `running` сделан лучше остального, но shutdown всё равно примитивный

```cpp
std::atomic<bool> running = true;
```

Использование atomic здесь уместно: main меняет значение, worker'ы читают.

Но завершение программы завязано исключительно на:

```cpp
getchar();
running = false;
```

Нет нормальной обработки console events, ошибок worker-потоков или другого shutdown path.

Если поток застрял в системном вызове, atomic сам по себе его мгновенно не отменяет.

## 31. `running` глобальный

Для маленькой одноразовой программы это работает, но архитектурно вся функция worker зависит от глобального состояния.

Это усложняет:

- повторное использование;
- тестирование;
- несколько независимых экземпляров;
- контролируемый lifecycle.

## 32. `WSAStartup/WSACleanup` размазаны по worker-потокам

Winsock имеет process-level initialization/refcount semantics.

Делать startup внутри каждого worker'а технически возможно при аккуратном парном cleanup, но здесь это:

- повторяет работу;
- усложняет error paths;
- создаёт ненужные состояния;
- уже содержит дисбаланс при раннем `return` после ошибки `socket()`.

## 33. Сообщение об ошибке raw socket вводит в заблуждение

```cpp
if (s == INVALID_SOCKET) {
    printf("raw socket не создан — запусти с админом\n");
    return;
}
```

Из того, что `socket()` вернул `INVALID_SOCKET`, вовсе не следует автоматически «не хватает администратора».

Правильная диагностика начинается с конкретного error code.

Сейчас автор вместо диагностики просто угадывает причину.

## 34. Администраторские права не гарантируют успешную отправку

Даже если raw socket удалось открыть, дальше влияют:

- ограничения Windows TCP/IP stack;
- firewall;
- security products;
- Winsock provider;
- routing;
- network interface configuration;
- upstream filtering.

То есть проверка «socket открылся» не подтверждает, что вручную сформированные датаграммы ушли на провод именно в представленном виде.

## 35. Upstream anti-spoofing существует независимо от Windows

Даже если представить ОС/драйвер, который позволит вывести forged source address, дальше трафик может фильтроваться:

- домашним роутером;
- VPN;
- хостинг-провайдером;
- ISP;
- датацентром;
- egress ACL;
- anti-spoofing правилами.

Поэтому «я записал любые четыре байта в Source Address» вообще не означает «Интернет примет такой пакет».

## 36. Нет выбора/проверки исходящего интерфейса

Код задаёт destination и отдаёт пакет `sendto()`, но не пытается понять:

- какой интерфейс выберет routing table;
- какой локальный адрес принадлежит интерфейсу;
- подходит ли source address политике этого интерфейса;
- что произойдёт при наличии VPN/нескольких NIC.

Для raw networking это существенно.

## 37. `target.sin_port` и UDP destination port дублируют информацию

Destination port уже записан непосредственно в UDP header:

```cpp
udp->dst_port = htons(target_port);
```

Одновременно он устанавливается в `sockaddr_in`, переданном `sendto()`.

Для raw sockets роль отдельных полей destination sockaddr зависит от Winsock semantics; наличие двух мест с одной и той же концептуальной величиной усложняет код и создаёт риск несогласованности.

## 38. Нет Path MTU awareness

Default size = `1400` выбран просто как магическое число.

Да, 1400 часто помещается в Ethernet MTU 1500 вместе с IPv4/UDP headers, но путь может включать:

- VPN;
- tunnels;
- PPPoE;
- другие encapsulation layers;
- меньший MTU.

Код вообще не интересуется MTU и возможной фрагментацией.

## 39. Fragmentation fields заполняются максимально примитивно

```cpp
ip->flags_off = 0;
```

Это одновременно означает отсутствие выставленного DF и нулевой fragment offset.

Само по себе для небольшого пакета это допустимо, но код не имеет никакой модели фрагментации, MTU или обработки связанных ICMP-сигналов.

То есть это не качественная реализация raw IPv4 sender — это минимальная заготовка полей «лишь бы было похоже на header».

## 40. TTL всегда одинаковый

```cpp
ip->ttl = 64;
```

TTL 64 — обычное допустимое значение.

Но вместе с остальным это ещё раз показывает, почему комментарий про «рандомный payload без сигнатуры» бессмыслен: большая часть packet metadata остаётся совершенно однообразной.

## 41. Нет анализа ICMP ошибок

При отправке UDP сеть может отвечать ICMP сообщениями — например, о недоступности назначения или проблемах фрагментации.

Программа ничего не читает и вообще не имеет receive/error-analysis path.

Для диагностического raw-socket приложения это серьёзный недостаток: оно умеет только слепо вызывать `sendto()`.

## 42. Нет подтверждения того, что реально оказалось «на проводе»

При работе с raw sockets важно различать:

1. что приложение положило в userspace buffer;
2. что принял Winsock;
3. что изменил/отфильтровал IP stack;
4. что обработал NIC/offload;
5. что реально покинуло интерфейс.

Этот код считает все пять этапов одним и тем же событием.

Это неверная модель.

Для безопасного лабораторного исследования подобные вещи обычно проверяются packet capture'ом на контролируемом интерфейсе/виртуальной сети.

## 43. Код не предназначен для IPv6

Везде жёстко задано:

```cpp
AF_INET
```

и используется IPv4 header.

Поддержки IPv6 нет вообще.

Это важно ещё и потому, что правила checksum у UDP/IPv6 отличаются: обычный нулевой UDP checksum для IPv6 недопустим за исключением специально определённых случаев.

## 44. В includes не хватает прямых заголовков для части используемых сущностей

Код напрямую использует:

- `uint8_t`, `uint16_t`, `uint32_t`;
- `printf`;
- `rand`;
- `atoi`.

Но не подключает явно стандартные заголовки вроде:

- `<cstdint>`;
- `<cstdio>`;
- `<cstdlib>`.

На конкретном MSVC часть объявлений может приехать транзитивно через Windows headers, и код случайно соберётся.

Но reliance на transitive includes — плохая практика и делает исходник хрупким.

## 45. `memset(packet, 0, sizeof(packet))` выполняется только один раз — здесь это не главный баг

Это иногда выглядит подозрительно, но основные используемые поля header перезаписываются в каждом цикле, а payload полностью заполняется заново для заданного `payload_len`.

Поэтому само по себе однократное обнуление не является главным дефектом.

Проблемы начинаются скорее из-за отсутствия проверки размеров и ручного type-punning.

## 46. Нет проверки частичной/неожиданной семантики отправки

Для datagram send обычно ожидается отправка всей датаграммы либо ошибка, но код всё равно обязан проверять return value.

Сейчас любое неожиданное значение полностью теряется.

Никакой статистики ошибок тоже нет.

## 47. Нет счётчиков и observability

Программа не знает:

- сколько вызовов `sendto()` было;
- сколько завершилось ошибкой;
- какие error codes встречались;
- сколько байт попыталась отправить;
- сколько worker'ов реально стартовало;
- какие worker'ы завершились раньше времени.

Поэтому надпись «spoof-флуд ...» — фактически просто декларация намерения, а не описание проверенного состояния.

## 48. Комментарии выглядят увереннее, чем реальная реализация

Самая опасная часть этого исходника с инженерной точки зрения — не отдельная строчка, а общий стиль:

- «raw socket не создан — значит нужен админ»;
- «checksum можно не считать»;
- «рандомный payload убирает сигнатуру»;
- «рандомный uint32_t = нормальный spoofed IPv4»;
- `Sleep(1)` якобы решает контроль нагрузки.

То есть комментарии маскируют большое количество допущений как факты.

Для сетевого low-level кода это особенно плохо: программа может выглядеть «рабочей» по stdout, хотя реальные пакеты некорректны, фильтруются или вообще не выходят с интерфейса.

# Что в коде всё-таки сделано концептуально верно

Чтобы аудит не выглядел как «тут неправильно вообще всё», несколько вещей имеют правильную базовую идею:

- `SOCK_RAW` + `IP_HDRINCL` — действительно механизм ручного предоставления IPv4 header в Winsock, где он поддерживается;
- `0x45` корректно кодирует IPv4 + 20-byte header без options;
- protocol `17` соответствует UDP;
- UDP header действительно 8 байт;
- при корректном `packet_size` выражение `UDP length = packet_size - 20` концептуально верно;
- destination/source ports переводятся через `htons()`;
- destination IPv4, полученный `inet_addr()`, уже представлен в network order;
- `std::atomic<bool>` подходит для простого stop flag между main и worker-потоками;
- `join()` после изменения stop flag — правильная базовая идея завершения thread pool.

Но этого недостаточно, чтобы вся программа была корректным raw packet generator'ом, и тем более недостаточно для заявленного spoofing-поведения на современной клиентской Windows.

# Самые критичные проблемы, если сократить до десяти

1. Windows ограничивает raw UDP spoofing с несуществующим локальным source IP.
2. `sendto()` полностью игнорирует ошибки.
3. `setsockopt(IP_HDRINCL)` не проверяется.
4. `WSAStartup()` не проверяется, а error path нарушает cleanup.
5. `fake_src` записывается без нормального учёта network byte order.
6. Один `std::mt19937` используется несколькими потоками без синхронизации.
7. `packet_size` позволяет выйти за `char packet[65536]`.
8. IPv4 header checksum оставлена нулевой с технически неверным оправданием.
9. `atoi()` и все числовые аргументы практически не валидируются.
10. Код вообще не подтверждает, какие пакеты реально покинули сетевой интерфейс.

# Итог

`udp_spoof_flood.cpp` выглядит как короткий proof-of-concept, написанный человеком, который примерно знает расположение полей IPv4/UDP, но сильно переоценивает то, насколько простой raw socket даёт контроль над реальным сетевым трафиком.

Основные классы проблем:

- неверные предположения о Windows raw sockets;
- отсутствие нормальной диагностики Winsock;
- потенциальные memory-safety ошибки;
- ошибки/неясности endianness;
- небезопасное использование PRNG в потоках;
- слабая валидация входных данных;
- слишком грубая ручная сериализация protocol headers;
- смешивание IPv4 checksum и UDP checksum;
- отсутствие проверки того, что реально вышло на интерфейс;
- комментарии, которые обещают больше, чем делает код.

В качестве учебного примера этот исходник полезнее разбирать на ошибки, чем использовать как образец сетевого C++.
